## 問題與限制

每張 Issue 都直接進 main 會把整合風險、完整 CI 成本與 release 頻率綁在一起；只跑快速檢查則無法證明完整 story 與 main 組合可交付。GitHub 的 branch／path skip 也可能讓 required context 永久 Pending。

## 決定

- `main` 是唯一永久 branch。Milestone work 進短命 `dev/m*`；standalone、hotfix 與 bot work 由短分支直接進 `main`。只有 Issue 明列獨立環境、soak／canary 目標與停止條件時，才使用一條短命 `dev/i*`。
- Main advance 不會批次回灌或使 ordinary delivery PR stale；各 Milestone 的 final Promotion PR 以精確雙親 bridge 同時納入 delivery source 與 current main，不另開 final sync PR。只有 owner 已在 PR 明列 dependency，或 `dev/i*` canary 要交付時，才使用 reviewed sync PR。無衝突 sync 先驗 exact refs、雙親、tree 與授權路由，再沿用 current main 的 fresh full evidence；人工解衝突只跑 affected owners 與 fast，promotion 才跑 final full。
- CI 分 policy、fast、full、scheduled／release 四層，以 stable aggregate context 收斂結果。
- Promotion 綁定 base／head SHA、candidate tree、full verification 與 canary 三態；artifact-only 不冒充 external canary。
- Quota fallback 已退役（Issue #1071，#1058 決定 3；現行規則見 [`docs/ci-policy.md`](../ci-policy.md)）：GitHub billing zero-step 不再是 required check 的例外，一般 PR 與 promotion 都沒有 quota-only 合併路徑；Actions 中斷時改走 governance-switch 路線，required checks、exact-head 授權與 remote lease 照常要求。
- 本 repo 已是 public repository（2026-10-19 讀回 `visibility: PUBLIC`），不再以「GitHub Teams private plan 結構性超出 Actions 額度」作為交付前提；原本據此自動化的一般 Issue PR quota fallback 隨 #1071 退役，理由保留在下方歷史 disposition。
- 14→3／4 job-minute 是明確標示的規劃估算；hosted duration 與 `ci-plan` 僅在 runner 可用時作 telemetry，不是交付關卡。Portable baseline 不要求管理員調整帳單、方案或維護額外 runner。
- Acceptance checklist 未完成時不得使用 closing keyword；PR metadata 從 linked Issue 同步 assignee 與 Milestone，並從 Issue native Type（或 Type 不可用時的 fallback Label）推導一個小寫 classification Label；離開 draft 時要求非作者 reviewer。CSARC-owned Milestone promotion 以 `Refs #tracker` 保持 tracker open，版本與 CHANGELOG 納入同一張 promotion PR；只有 Release 發布驗證成功（或同一 release workflow 明確判定 `no-release`）才補齊 evidence、關 tracker 與 Milestone（#871）。
- Draft push 上限為 risk-owned fast；ready event 對同一 exact head 重新升級。metadata-only event 只有在 repo/head/tree/base、resolved tier/scopes/command/toolchain、labels、release level 與 24 小時 freshness 全同時，才能直接引用一次原始 hosted Execute；新 head 永不沿用。
- Routine verification 保留一個 `ci_tier.py` router 與一個 `verify` required context。#876 把沒有獨立執行內容的 `baseline`／`docs` 名稱收斂成 `fast`；docs／dependency scope 不執行無關 Python regression。真實 Copier create／adopt／previous-release update 與 Rust native 代表 canary 留在 full，不建立逐測試 cache 或 evidence DAG。
- Hosted 模式由 owner 跑 focused checks、required `verify` 在 exact candidate 執行所選 fast／full 一次；不再因 stable 或高風險路由要求 owner 先於本機重跑同一套 full。Local 模式的 exact-head self-attested evidence，以及 Actions／發布 fallback 明定的本機 full，不受此收斂影響。
- TDD 留下最小 regression 與最終 evidence，不保存逐次 red／green 暫態。
- 合併的 tree 等於證據的 tree（#1073）：`pr_lifecycle.py merge` 在呼叫 merge API 之前要求 lease 的 `base_sha` 是 head 的祖先（compare 為 `ahead` 或 `identical`），否則拒絕並要求先合併最新 base、重新取得證據；因為 head 包含 base，squash tree 就是 head tree，合併前先讀回 head commit 的 tree，必須等於 lease 與證據綁定的 tree。合併後讀回 merge commit 的 tree 與 trailer，與證據 tree 或算出的 trailer 不一致就以非 0 結束，並在 summary 狀態記錄 `tree-mismatch`／`trailer-mismatch`。所有合法 route 與兩種 `verification_mode` 都走同一個 merge 呼叫。
- 證據雜湊契約（local 與 hosted 共用）：payload 是一個 JSON 物件，帶自己的正整數 `schema_version`，不含自己的 digest 或 locator；canonical 規則是 RFC 8785（JCS）的子集：UTF-8 無 BOM、ASCII 且不重複的物件鍵依 code point 排序、無多餘空白、只允許 −(2^53−1) 到 2^53−1 的整數（不允許浮點數、NaN、Infinity、指數）、字串必須是有效 Unicode scalar value 且已是 NFC、`started_at`／`completed_at` 一律 `YYYY-MM-DDTHH:MM:SSZ`、集合性質的陣列（`scopes`、`toolchain`、`labels`、`runner_labels`）先排序。超出子集的值由產生端拒絕，不靜默轉換；在子集內 `json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("utf-8")` 與 JCS 相同。digest 是 `sha256:` 加 canonical bytes 的小寫 hex；驗收端重新序列化讀到的 payload，要求 bytes 完全相同再算 digest。envelope（`envelope_version`、`digest`、`trust`、`route`）不參與雜湊；locator 是 summary 留言自己的 URL，寫在 `CSARC-Evidence` trailer。讀取端接受任何正整數版本並以 digest 驗證全部 bytes，所以 K1（#1079）在 payload 加欄位、提升版本後，既有紀錄與新紀錄都能驗證。實作是 `scripts/merge_trace.py`（與 `.csarc/scripts/`、`src/csarc_cli/` 的副本逐位元組相同）。
- Durable summary：每張 PR 至多一則以 `csarc-merge-evidence: v1` 開頭的留言，內含狀態段（`status: attempt|merged|tree-mismatch|trailer-mismatch` 與 trace 行）以及 envelope 和 canonical payload bytes。lifecycle 在 merge API 之前建立它，或在狀態仍是 `attempt` 時以最新 attempt 原地取代 payload（同一 attempt 重試不改寫）；這是合併前唯一的寫入。狀態離開 `attempt` 之後 payload 不再改變，lifecycle 拒絕改寫；只有狀態段會更新。出現一則以上 marker 留言時拒絕合併。`merge-trace`、`bypass-trace`、`copilot-review-trace` 與 `local-verification-trace` 只在合併讀回之後寫進狀態段，帶 `merge=<SHA> evidence=<locator>`，不再另外散落成多則留言。留言與 repository 同存、CSARC 不刪除，但有寫入權限的人仍可編輯或刪除；default branch 上的 trailer digest 可以偵測異動，紀錄不存在是 `evidence-missing`、重新計算不符是 `evidence-digest-mismatch`。local 的 `.git/csarc/local-verification/<head>.json` 只是快取，不是稽核來源。hosted payload 由 `require_trusted_verification()` 推導的 repository、head、tree、base、tier、scopes、command、toolchain、runner labels、run ID 與 attempt、job ID、check run ID、App integration ID、結論與 `started_at`／`completed_at` 組成，不依賴 Actions artifact。限制：Actions 資料到期後，digest 只證明紀錄自合併以來沒有被改過，不能再獨立證明當時的 API 事實。
- 每一條合法 route（`issue`、`sync`、`dependabot`、`release-recovery`、`hotfix`、`release-follow-up`、`milestone`、`isolated`）都由 lifecycle 寫同一組 squash trailer：`CSARC-Evidence`（locator）、`CSARC-Evidence-SHA256`（digest）、`CSARC-Evidence-Tree`、`CSARC-Trust`（`self-attested-local`／`github-hosted`）、`CSARC-Route`、`CSARC-Approval`（lifecycle 的 `authorization_source`：`comment`、`review`、`copilot`、`hotfix-emergency`）與 `CSARC-Authorization`。鍵名與值域存在機器可讀的 `policies/merge-trailers.json`（generated：`.csarc/policies/merge-trailers.json`），寫與驗都讀這份檔，缺少時 lifecycle 拒絕合併；缺鍵、重複、值域外或與讀回不符都 fail closed。這份檔也是 governance baseline 的 writer 標記。squash message 先保留 PR commits 中每個完整的 `BREAKING CHANGE:`／`BREAKING-CHANGE:` footer（含延續行，#1104），再以空行隔開 trailer 段落，release bump 不變。trailer 是合併後的稽核紀錄，不是證據，不能滿足 `verify` 或任何合併、發版閘門（#661 不恢復）。GitHub UI 合併、`merge_mode: human-only` 之後的人工合併與 `gh pr merge --admin` 例外不是合法 route，沒有 trailer。
- Governance baseline（`csarc status`、`merge_trace.py audit` 與之後的 publisher 共用）：baseline 是 first-parent 歷史中，第一個能以可信的安裝 provenance 證明「已安裝的 CSARC Release 含合併 trailer writer」的 commit；template 來源 repository 本身以自己的 tree 為準；證明不了時結果是 `inconclusive`，必須明確確認，不猜測，也不新增設定。每個 commit 依序判定：tree 沒有契約檔為 `absent`；GitHub 回報的 repository `id` 與 `full_name` 等於 canonical 且設定沒有 `_commit` 為 `contains`（fork 不適用）；`.csarc/provenance.json` 的 `verification` 是 `verified`、`schema_version` 是 1、`repository`／`repository_id` 是 canonical、`release_tag` 非空而且 `commit_sha` 等於同一 commit 的 `_commit` 為 `contains`；其他為 `unresolved`。歷史 provenance 只做欄位檢查，不重新解析 Release。第一個 `contains` 之前沒有 `unresolved` 就以它為 baseline（`resolved`），有則 `inconclusive`；都沒有為 `not-installed`。`inconclusive` 以 `csarc status --confirm-governance-baseline <SHA>`（或 `merge_trace.py audit --confirm-baseline <SHA>`）從候選清單確認，結果 `confirmed`。
- Baseline 之後 default branch 的每個 first-parent 合併分類為 `traced`、`untraced`、`tree-mismatch`、`evidence-missing`、`evidence-digest-mismatch`、`trailer-invalid` 或讀不到 GitHub 的 `inconclusive`。`csarc status` 把 `untraced` 與 `inconclusive` baseline（沒有檢查任何合併）只列為提示，其他發現為阻擋項目並以 1 結束；release path 以 `merge_trace.py audit --strict` 執行，`untraced` 與 `inconclusive` baseline 也阻擋，讓 `csarc-owned` 的發版可以 fail closed（publisher 本身由 #1074 實作）。

## Ownership 與驗證

Issue owner 負責 scope 與 acceptance；delivery owner 負責 sync conflict 與 promotion；workflow 保存 machine-readable route／evidence。完整操作以 `AGENTS.md` 與 `docs/ci-policy.md` 為準，行為由 policy fixtures、生成專案與 live probes 交叉驗證。

## 評估過的替代方案

| 方案 | 結論 |
| --- | --- |
| 每張 PR 都跑完整矩陣 | 不採用作日常預設；重型驗證移到 ready 的 full boundary、promotion／hotfix |
| 用 branch 名稱直接把 sync 降級 | 不採用；名稱只能觸發可信 preflight，必須再驗 route、live refs、雙親、tree 與 main full evidence |
| 逐測試 cache／跨 commit evidence DAG | 不採用；只保留 coarse risk scopes 與同 head、單跳的 hosted evidence reuse |
| 只用 path filter 跳過 workflow | 不採用；required context 可能永久 Pending |
| 為每張單建立 Milestone | 不採用；Milestone 只代表可獨立驗收的 story outcome |
| 把本機 quota fallback 當 hosted CI 或 release 成功 | 不採用；只能留下受限 attestation，額度恢復後仍須補跑 |
| 逐 PR 要求 human 區分「額度用盡」與「付款失敗」才能觸發 quota fallback | 不採用；GitHub 的 runner 訊息本身把兩者寫在同一句、機器無法區分，逐 PR 要求人工判讀對稽核而言是不必要的儀式，改為機械式 zero-step 偵測＋一次性接受這是 Teams private plan 的常態限制；該自動化已隨 quota fallback 退役（#1071） |
| 一般 Issue PR 比照 promotion 維持 attestation＋authorization 雙留言 | 不採用；promotion 是實際 release 邊界才需要雙方確認，一般 PR 只需機械式 zero-step 確認＋本機驗證＋說明留言；quota fallback 已退役（#1071），本列只保留歷史理由 |
| 要求管理員恢復 hosted runner 才完成交付 | 不採用；runner 是外部 capability，可用時收集 telemetry 即可 |

## 重新評估條件

Hosted runner 可用時收集 duration、job-minute、billed minutes 與 `ci-plan` telemetry 校準模型；repo 轉為 public 後不再受 Teams private 額度限制，#189 的量測改由 hosted telemetry 補足；量測缺漏不阻塞交付，也不影響本 ADR 其餘決定。若實測成本、false routing 或 promotion latency 與模型顯著不符，以新 Issue 調整；telemetry 不可用不降低安全與 full gate。#812 先要求 exact effective suite/scopes 才能沿用；只有在量測證明值得時，才考慮讓較高 tier／scope 超集合覆蓋較低需求。
