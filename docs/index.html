步驟 2｜先定 AI 契約，再開始實作

基本導入。AI 先讀工作單、repo 與 AGENTS.md，再提出做法、修改、測試；人保留方向、風險與合併責任。

問題與目的｜只給一句 prompt，AI 會猜範圍；規則寫太滿又會過時。契約要短、可執行，且不能取代人的判斷。

其他常見做法

不靠長提示詞，也不把責任交給 AI

  • 只給一句 prompt：AI 會自行猜範圍與完成條件
  • 複製全部 coding style：容易與 Ruff／Biome 分歧，固定判定應交給 CI
  • AI review 當必要門禁：結果會漂移，不能取代測試、同事審查與 Ruleset
我們的選擇
標準 AGENTS.md＋就近覆寫

agentsmd/agents.md｜MIT｜公開且持續維護；格式就是一般 Markdown。

熱門實例：VS Code 根檔 5 行、uv 25 行、Kubernetes 36 行；Next.js 558 行反映大型 monorepo，而不是每案都該追求的長度。

官方行為：Codex 會由根目錄往工作目錄合併指令，越靠近目前檔案的規則優先。

Ref. OpenAI Docs; agentsmd/agents.md repository.

工作契約：六段涵蓋範圍、工作迴圈、指令、修改界線、安全與審查；依語言只列真正存在的指令，根檔最多 200 行。
AI 執行：讀資料、提計畫、修改、補測試、跑共同驗證並整理 PR。
人類負責：確認需求與技術方向、判斷風險、審查差異；真正門禁仍是 CI、Ruleset、CODEOWNERS 與 Actions 權限。

設定方式
  • 人類入口與 AI 工作契約：README.md 規範八個必要章節；AGENTS.md＋CLAUDE.md 規範 Agent
  • 實際驗證：生成 repo 與其 CI 執行 scripts/verify；只有中央模板 repo 執行、不下發的 scripts/verify-template.sh 負責建立／導入／更新 fixture
  • 唯讀權限、人類核准與指定審查者：policies/actions.json＋policies/rulesets.json＋CODEOWNERS

先辨識 GitHub 方案，再套用真的能生效的管制

基本導入｜同一份公版依 Free、Team、Enterprise 與實際 API 能力調整；不把付費功能假裝成已啟用。

目前實測｜Innoguard-Cyber-Arch API 回報 Free＋private；因此 main 現在確實沒有強制保護，CI 紅燈仍可能被有權限者繞過。

Free 目前

保存政策，check 降級放行：public repo 直接強制 Ruleset；private repo 只把期望狀態保留在 policies/rulesets.json，因為 REST 與 GraphQL 建立 API 都會拒絕。check 標示 DEGRADED，CI 與 release 照常執行，PR 會留下警告留言。

  • private repo 的 main 仍未受 Ruleset 保護
  • CI 與留言提供紀錄，但無法取代 merge gate

Team 最低建議

再加上：private repo Ruleset、protected branches、必要審查、team reviewers、CODEOWNERS 與必要檢查。

  • 需先建立真實 CODEOWNERS team
  • 公版即可套用現有 repo Ruleset

Enterprise 組織級

再加上：SAML SSO／SCIM、internal repo、private/internal 部署保護、私有 Pages、稽核串流與 IP 限制。

  • 組織／Enterprise Ruleset 可集中治理
  • 目前只偵測並提示，不自動改組織設定
部署原則plan 先查帳號方案、repo 可見性與 Ruleset API；Free private 仍會套用基本設定，並把期望 Ruleset 保留在 repo，等 repo 改為 public 或組織升級後再由 apply 套用。Web UI 可供管理員人工預建 disabled Ruleset，但公開 REST／GraphQL API 無法自動建立。腳本本身不會改可見性。依序執行 plan、apply、check；不支援強制時，check 回報 MISSING 或 STAGED 與 DEGRADED，CI、release 繼續，PR 留言保留稽核紀錄。已支援 Ruleset 卻規則對不上政策時仍 fail-closed。啟用前必須確認 CODEOWNERS team；Enterprise 的身分、網路與稽核政策另經組織層審查；Code Security／Secret Protection 另購。
設定方式
  • 查方案與 API：scripts/apply-repository-settings.sh plan
  • 套用支援的設定：scripts/apply-repository-settings.sh apply
  • 區分 policy、遠端儲存與有效強制：scripts/apply-repository-settings.sh check
  • 排程偵測漂移：.github/workflows/governance-drift.yml（daily cron）每天在 CI 之外重跑 check，抓出排程執行時仍存在的偏離，並由 scripts/check-governance-drift 自動開立或更新追蹤 Issue；兩次快照之間曾變更又恢復的事件仍需 audit log 或組織層監控，下發專案以 enable_governance_drift_check 選配

Ref. GitHub plans；About rulesets. Accessed August 21, 2026.

步驟 3｜本機與 CI 用同一把尺

基本導入。本機先跑 ./scripts/verify；PR 與推送選定整合分支時，CI 再執行完全相同的入口。

問題與目的｜若每個人和 AI 都用不同指令，結果就無法重現；統一成一個驗證入口，問題可在送出 PR 前發現。

其他常見做法

這次不選，因為會出現兩套標準

  • 只靠 IDE／pre-commit：本機可跳過，不能作合併證據
  • 每個 workflow 重寫指令：本機綠燈不代表 CI 會綠
  • ESLint＋Prettier：TypeScript 基線先用一份 Biome 設定，減少重疊
  • Python flat layout：測到原始碼，不是真正會發布的成品
我們的選擇
Python：uv／Ruff／mypy／pytest　TS：pnpm／Biome／Vitest

uv／Ruff、Biome、Vitest 與 Gitleaks 都是公開且持續維護的主流工具。

選型：各語言用自己的格式、型別、測試與打包工具；安全與治理入口仍共用。

Python：Ruff、strict mypy、pytest、80% coverage、wheel 隔離安裝；需要舊版時再驗最低 Python 與相依下界。
TypeScript：Biome、strict TypeScript、Vitest 80% coverage、npm tarball 隔離安裝；Node 24＋pnpm 11。
Coverage：新案用 global coverage 建立基線，既有案先用 diff coverage 約束 changed lines。百分比只指出未測程式碼，不代表測試品質，也不取代風險分析與人工 review；只有缺陷紀錄、關鍵模組或風險改變時才調整門檻，不要為提高數字加入沒有驗證行為的測試。
共同：./scripts/verify 跑啟用模組與 PR 政策正反例；公版另注入不合法程式，確認門禁真的會拒絕。

設定方式
  • 宣告 CI/CD-only、Python、TypeScript 或兩者：.csarc/profile.json＋scripts/detect-language-profile
  • Python 規則／鎖定：pyproject.toml＋uv.lock　TypeScript：package.json＋tsconfig.json＋biome.json＋pnpm-lock.yaml
  • 驗證入口與拒絕測資：scripts/verify＋scripts/test-pr-policy＋.github/workflows/ci.yml

步驟 1｜先寫清楚要解決什麼

基本導入。可選 Story Milestone 管完整成果，1..N Issues 管可獨立工作，PR 只交付其 Issue；不是每張 Issue 都需要 Milestone。

寫作原則｜Issue 標題用英文摘要成果；內文再以中文交代問題與完成條件，其餘選填寫進補充。

其他常見做法

不讓每張工作單都走過重流程

  • 只寫 Issue 標題：缺成果與驗證，人和 AI 只能猜
  • 每張都跑 Spec Kit：小工作成本過高
  • 只留在聊天：無版本紀錄，不能在 PR 審查
我們的選擇
預設 spec → Issue；明確 story 才同步 Milestone

目前：docs/specs/ 經 CI 驗證；預設 idempotently 建立或更新單一 Issue，只有 frontmatter 明列 tracking: story 才建立或更新 Milestone，不自動拆 child Issues。

生命週期：最後一張 open Issue 關閉時關閉 Milestone；Issue reopen 或 open Issue 掛入 closed Milestone 時重開。每次都讀最新 API 狀態並以 Milestone number 序列化。

Spec Kit：github/spec-kit｜MIT｜公開、未封存、持續維護。

Story：Milestone description 填 Problem、Outcome、Acceptance criteria、Out of scope、Verification 與來源；只掛直接推進成果的 Issues，不重複掛 PR。
Issue：12–80 個英文 ASCII 字元、至少三個詞；standalone 工作可不掛 Milestone，必要 fix 可加入既有 open story。
既有 repo：分頁唯讀盤點、小批提出候選分群與排除項目，經人確認才 idempotently 套用；不靠標題或 label 自動判斷。

設定方式
  • Story 結構：docs/milestone-description.md；agent 先查 open Milestones，再選沿用、新建或 standalone
  • Spec 同步：scripts/spec_to_issue.py；預設 Issue，tracking: story 才同步 Milestone
  • 自動收尾：milestone-lifecycle.yml 依最新 open issue 數關閉或重開

Ref. GitHub issue types; Issue Forms syntax; GitHub labels; Spec Kit. Accessed August 23, 2026.

步驟 4｜小 PR 通過證據再合併

基本導入。沒有共用測試環境就直接或經 stack PR 到 main；真的有 dev 環境，才加 dev 整合層。

問題與目的｜分支要對應真實用途；無條件多一層 dev 只會增加漂移與合併衝突，不能取代測試環境。

其他常見做法

不把 dev 當成形式上的必經站

  • 預設 main-only：Issue → 短分支 → PR → main，適合沒有共用測試環境
  • 有 dev 環境：Issue → 短分支 → PR → dev，再經升版 PR 進 main
  • 直接 push：兩種模式都禁止，不能繞過審查與檢查
我們的選擇

建立時選分支模式，Issue-first 規則不變

工作分支：type/<Issue 編號>-簡稱；PR 可直接進策略分支，或指向 open PR 的上游分支形成 stack，但整條鏈必須回到策略分支。PR 內文必須用 Closes #編號 連回同一張未結案 Issue。
PR 分類：GitHub 沒有 PR Issue Type／Issue Form，因此使用 Markdown template，並恰選一個 label：fix→bug、docs→documentation、其他允許的 title type→enhancement。
範圍：需求超出完成條件就另開 Issue、分支與 PR；只有依賴／版本自動化，以及未改檔案的 duplicate triage 可免 Issue 或 PR。

設定方式
  • 選 main-only 或 dev 模式：copier.yml → branch_strategy，結果存入 .csarc/profile.json
  • 核對標籤、Issue、分支編號、PR 目標與標題：.github/workflows/pr-policy.yml＋scripts/test-pr-policy
  • 保護選定分支並指定審查者：policies/rulesets.json＋.github/CODEOWNERS；Free private 保存 policy 並留下 CI／PR 紀錄，但不能自動建立或強制 Ruleset

步驟 5｜風險立即看見，升版不搶第一天

基本導入。安全、檔案證據與「版本能否安裝」是不同問題；依賴更新也是日常維護的一環。

問題與目的｜第三方套件出現漏洞時要立刻知道；一般新版則先等三天，避免成為供應鏈攻擊最早一批受害者。

其他常見做法

不把所有風險都當成同一種更新

  • 新版一出就升：可能成為惡意版本最早一批使用者
  • 漏洞也等三天：已知風險不應延後處理
  • 現在就換 Renovate：已評估方案，暫緩換手
我們的選擇
Dependabot＋OSV＋anchore/sbom-action 已完成

OSV-Scanner｜Apache-2.0；Syft｜Apache-2.0。

Renovate：AGPL-3.0；已評估以單一設定取代 Dependabot cooldown 與 pnpm minimumReleaseAge（見下方「評估」卡片）；trustPolicy: no-downgrade 是獨立的發布者信任保護，仍留在 pnpm。下游 repo 的 GITHUB_TOKEN 無法觸發 Renovate PR 上的必要檢查，換手前要先解決這個營運缺口，暫緩實際遷移。

等待：Dependabot 一般升版先等三天；pnpm 另以嚴格 resolver 阻擋發布未滿三天的直接或間接套件，並拒絕 publisher trust 降級。遇到 trust downgrade 時先確認發布者與 provenance，不要直接停用 policy。
漏洞：OSV 對已公開漏洞立即通知，不套用等待期。
內容：uv.lock 保存 SHA-256；pnpm-lock.yaml 保存 integrity hash；發布時解壓真正成品，再附 checksum 與非空 SBOM。
限制：雜湊不證明來源善意，SBOM 也不會自行阻擋漏洞。

設定方式
  • 兩種生態的一般升版等三天：.github/dependabot.yml；pnpm 本機也嚴格等待：pnpm-workspace.yaml
  • 凍結安裝並比對兩種 lockfile 雜湊：scripts/verify
  • 掃已知漏洞：osv.yml　發布 checksum／SBOM：release.yml
  • 回報本專案自身的漏洞：SECURITY.md；不寫死聯絡信箱或 SLA，由專案 owner 填入實際通報管道

中央共用更新規則（preset）是什麼？

白話說：把套件更新規則放在一個共用設定；其他 repo 只要寫「沿用這套規則」，之後改一次就能同步等待天數、排程與分組。

何時需要：repo 變多、各專案設定開始不一致，或 Dependabot 已無法表達共同規則時。

目前決定（已評估觸發條件）：已提出具體 Renovate 設定草案，把 Dependabot cooldown 與 pnpm minimumReleaseAge 合併成一份「新版本觀察期＋已知漏洞立即處理」設定（見依賴風險卡片的「評估」項）；pnpm 的 trustPolicy: no-downgrade 不屬於等待期，繼續獨立保留。因下游 repo 用預設 GITHUB_TOKEN 自架 Renovate 時，PR 不會觸發必要檢查，換手前要先解決這個問題，本次先記錄方案、暫緩實際遷移，後續換手另開 Issue。

步驟 6｜版本規則與成品接續

Release 與成品工作流已明確接續：公版本身與每個生成 repo 各有一個 SemVer；release-please 使用內建 GITHUB_TOKEN，建立 release 後以 tag dispatch 成品工作流。

設計流程｜fix(ci) 升 patch、feat(python)／feat(typescript) 升 minor、任何不相容變更加 ! 升 major；Release PR 合併後才建 tag。

其他常見做法

不為版本號另加一套平台

  • Changesets：適合 npm workspace；CI-only／Python 案會多背 Node 設定
  • Nx release：適合既有 Nx 大型 workspace；本案只需一個 release unit
  • profile 各自編號：會增加相依矩陣與升級對版成本
我們的選擇
release-please＋單一 SemVer

googleapis/release-please｜Apache-2.0｜持續維護。

採用原因：manifest 模式與 extra files 已能用一個 release unit 同步不同 profile 的版本來源，沒有必要再引入 Changesets 或 Nx。觸發邊界：Actions policy 允許只有 release job 取得 pull-requests: write；release 建立後，另一個只具 actions: write 的 job 以輸出的 tag dispatch 成品 workflow。一般 main push 不會重複交付。

Ref. GitHub workflow trigger docs and live workflow runs, accessed August 23, 2026.

公版：version.txt 是唯一版本來源，四種 profile 共用 vX.Y.Z。
生成 repo：各有一個 SemVer；release 建立後使用同一個 tag 自動接續既有成品工作流。

設定方式
  • 公版單一版本：version.txt＋.release-please-manifest.json＋release-please-config.json
  • 依 profile 同步版本來源：CI/CD-only 用 version.txt；Python 用 pyproject.toml；TypeScript 用 package.json；混合案同步後兩者
  • 成品接續：release-please 的 release_created／tag_name 輸出只在新 release 建立時 dispatch 成品 workflow
目前邊界版本資料、CHANGELOG 與成品 workflow 已存在，但線上自動交付尚未端到端成功，所以不宣稱零設定或無人值守發版。GitHub App 目前只留給 python-version-policy.yml 的排程升版 PR 使用。

分階段導入，每一步都能驗證，也能停下來

三層導入｜基本能力現在就隨模板產生；未來與可選能力先寫清楚觸發門檻，不用空檔案假裝完成。

問題與目的｜一次導入模板、CI、部署、監控與 AI，團隊很難判斷哪裡出錯；分期後每一步都有完成條件。

其他常見做法

不按聲量或日期一次把功能全打開

  • 一次切換：錯誤會同時擴散到所有專案
  • 固定日期解鎖：時間到了不代表使用條件已成熟
  • 所有語言同時上：未驗證的 profile 只是空承諾
我們的選擇

三層不是日期，而是導入條件

基本導入：CI/CD-only、Python-only、TypeScript-only、混合 profile，以及 Issue／spec、PR／CI、本機驗證、OSV、依賴政策與 repo 內部網站已完成。Free 會先查能力並套可用設定；private repo 不宣稱有 Ruleset 強制保護。
仍在試行：release-please、可追溯成品與 attestation 要以 GitHub 線上執行驗證；至少一個真實下游 repo 完成建立與 Copier 更新後，profile 才有 beta 的採用證據。
未來／可選：中央 catalog／治理平台、多 repo、Go／Rust、網站託管／登入、Hugo、部署、監控、RAG、自主 Agent。

設定方式
  • 哪些 profile 已可用或仍在規劃：profiles/catalog.yaml
  • 先查方案再套可用設定：scripts/apply-repository-settings.sh；Ruleset／App 條件備妥後再啟用
  • 建立與更新路徑是否都能通過：scripts/verify-template.sh

Copier 保持同步，公版本身也吃自己的規則

基本導入。template/ 是下發內容唯一來源；root 只因 GitHub 讀取慣例保留公版自己的治理設定，21 對逐位元組相同的檔案由產生腳本從 root 生成 template/ 副本。

問題與目的｜模板錯誤會一次影響多個專案；每次修改都要真的建立新案、導入既有案，再讓已導入的 repo 接收更新並通過完整驗證。

其他常見做法

這次不選，因為無法持續同步或驗證

  • GitHub Template：只複製一次，不記得來源與答案
  • PyScaffold：可參考 Python 結構，但會形成第二套更新機制
  • 只驗 YAML：無法證明新案、既有案與更新真的能跑
我們的選擇
Copier＋root dogfood＋建立／更新回歸

copier-org/copier｜MIT｜公開、未封存且持續維護。

採用原因：記錄來源、語言與答案，能把新版模板套回既有 repo；衝突留給 PR 由人處理。

建立：CI/CD-only、Python-only、TypeScript-only、混合與最低 Python 都實跑驗證。
導入與更新：先以 existing mode 導入已有內容，再對同一 repo 執行下一版 Copier update、確認產品目錄未被覆寫，最後執行生成專案的完整驗證。
版本：公版四種組合共用一個 SemVer；Python 與 Node 基線則各自滿三十天觀察後再前進。

root／template 配對檔案｜21 對 workflow、policy 與 script（例如 zizmor.yml、policies/actions.json、scripts/spec_to_issue.py）在 root 與 template/ 之間逐位元組相同；過去只靠 verify-template.sh 在 CI 用 diff 事後比對，任何一邊漏改要等驗證跑完才被抓到。現在 scripts/sync-paired-files.sh 把 root 當成唯一來源：本機執行它會立即重新產生每個 template/ 副本；加 --check 則不寫檔，只驗證每個副本是否符合產生腳本的確定性輸出（內容與可執行位元），任何一對不一致就印出差異並失敗。verify-template.sh 已改成呼叫 --check，並用一段複製到暫存目錄、蓄意注入內容與權限落差、確認失敗、重新產生、確認通過的回歸測試證明這個機制會擋下漂移。dependabot.yml、.gitignore 等僅因 Jinja 變數不同的檔案不在此列，仍由既有的「產生一個實案並與 root 比對」測試把關；AGENTS.md／README.md 等文件因 root 與下游專案的治理內容本來就不同，不屬於重複維護，故未強行合併。

設定方式
  • 下發來源、語言組合、保留路徑與功能開關：template/＋copier.yml
  • root-only CI 與建立／導入／更新驗證：.github/＋scripts/verify-template.sh；生成 repo 不會收到這支腳本或 template release workflows
  • 語言基線與三十天觀察：profiles/catalog.yaml；Python 自動升版：python-version-policy.yml
  • root／template 配對檔案的單一來源與漂移檢查：scripts/sync-paired-files.sh

網站已入 repo，託管與登入分開決定

基本導入。docs/index.html 是公版內部網站；生成專案會收到可更新版型與自行維護的內容檔。

問題與目的｜README 只留開始使用與日常入口；完整設計放在 repo 網站。網站內容與發布平台分開，避免還沒決定託管就建立空架構。

其他常見做法

目前不選的原因

  • README 承載全部內容：接手者難以找到開始指令
  • 直接導入 Hugo：單頁內容還不需要建置鏈與主題相依
  • GitHub 私人 Pages：組織需 Enterprise Cloud；目前不適用
  • Cloudflare Pages＋Access：是免費候選，但登入與資料政策尚未確認
我們的選擇
Plain HTML＋專案內容模板

目前可用：公版網站位於 docs/index.html；生成專案使用同風格的單頁版型，不需額外框架或套件。

更新邊界：公版維護 docs/index.html 版型；專案維護 docs/site-content.js 內容，Copier 更新不覆寫後者。

仍待討論：Cloudflare Pages＋Access 是託管與登入候選；文件成長到需要多頁與搜尋時，才導入 Hugo＋Hextra。

版型：template/docs/index.html.jinja 隨 Copier 更新。
內容：template/docs/site-content.js.jinja 首次產生後由專案維護。
限制：noindex 不是存取控制；未實裝託管前，不宣稱網站已有登入保護。

設定方式
  • 公版完整說明：docs/index.html
  • 生成專案版型：template/docs/index.html.jinja
  • 專案內容與更新保護：template/docs/site-content.js.jinja＋copier.yml

決策附錄

存取控制決策｜託管方案未定前的臨時防護

評估三種存取控制方案的成本與限制；正式方案定案前，先以 noindex／robots.txt 與明顯提示做臨時防護，這不是存取控制。

Cloudflare Pages＋Access 候選

成本：免費額度可覆蓋小團隊登入牆；設定 Zero Trust 政策、網域與 DNS。限制：需要另建 Cloudflare 帳號與組織身分整合（Google／GitHub SSO 或 email OTP），資料與稽核政策需先確認。持有者：需組織 owner 建立並持有 Cloudflare 帳號權限，本 Issue 不建立或設定。

GitHub Pages＋IP 限制 受限

成本：沿用既有 GitHub 組織，不需另一個外部帳號。限制：私有 Pages 網站限定 GitHub Enterprise Cloud；IP allow list 對遠端／混合團隊不易維護，且組織目前是 Free plan，尚未具備此能力。持有者：需組織 owner 先升級方案，才能設定 Enterprise 網路政策。

內部登入平台（Backstage／Confluence 等） 未來
