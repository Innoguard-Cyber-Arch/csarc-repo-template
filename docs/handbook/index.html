repo-template 技術手冊

repo-template（Innoguard-Cyber-Arch/csarc-repo-template）是架構組維護的 Repository 模板；csarc 是呼叫模板能力的 CLI 名稱。本手冊定義產品政策、使用者承諾、操作方式及限制。

適用範圍：本手冊描述首個完整實作本文能力的 stable release；實際使用版本、來源與 full SHA 以該 Release 的 release-prompt.txt 為準。候選版本未通過手冊、SPEC、Repository 規則、程式與測試的一致性檢查前，不得宣稱已提供本文能力。

目前狀態：M18 已於 2026-10-18 發布 stable（v0.35.2）；本文的 CLI、Ready、migration 與 Roadmap 能力自 v0.35.x 起提供。版本：2026-10-19；核准 SHA-256 見 manifest。

1. repo-template 的功能與使用方式

1.1 repo-template 會替專案做什麼

1.2 Prompt-first 操作流程

使用者以自然語言描述要建立、導入、修改或交付的工作；AI 先讀取 Repository 規則並驗證 release-prompt.txt，再透過固定版本的 csarc CLI 判斷狀態、顯示計畫並等待確認。確認後才套用，後續日常工作由 Repository 工具箱執行；使用者不必記指令，實際操作仍由可重現的程式完成。

1.3 責任與能力邊界

角色負責不負責
使用者定義問題與驗收條件、確認風險、審閱產品結果、授予必要權限。不必自行設計 CI；仍須保留產品與高風險決策。
AI agent依 Repository 規則實作、執行檢查、整理證據與交接狀態。不得擴大範圍、繞過控制或宣稱未取得的證據。
repo-template產生設定、政策、驗證與生命週期工具；條件不足時停止或降級。不取代產品測試、法遵、正式環境核准或組織管理權。
GitHub保存 Issue、PR、review、Actions、Project、Release 與稽核紀錄。能力仍受方案、visibility、權限、政策及額度影響。

責任與邊界：AI 產生的程式碼由指派 agent、實際主導修改的人負責；合併者可以是同一人或 reviewer。repo-template 不承諾無人監督開發，也不取代產品測試、部署核准、法遵判斷或 GitHub 付費能力。

2. 安裝與導入

2.1 前置條件

create 在不存在、空的資料夾，或只含 .git、尚無 commit 與 tracked 檔的 repository 執行；adopt 與 update 在既有 Git repository 根目錄執行。一律需要 Git、uv／uvx、GitHub CLI 2.93.0 以上並完成 gh auth login；Windows 須在 WSL2 操作。下文的 csarc 代表 release-prompt.txt 給出的固定版本呼叫。選用語言另需該 Release 指定的工具鏈；ProjectV2 需要 project scope，Ruleset 與 Release 設定需要 repository admin。

2.2 給 AI agent 的啟動 Prompt

這段 Prompt 是建議入口。它要求 agent 從已發布版本取得固定內容，不直接使用 main，且在使用者確認前不得寫入：

請從 https://github.com/Innoguard-Cyber-Arch/csarc-repo-template
的 published Releases 中，依官方 csarc CLI 選出最新 stable 且 immutable
的 Release，下載並讀取它的 release-prompt.txt，確認附件內的 repository、
tag 與 full SHA 一致後，完全依該 prompt 在目前 workspace 繼續。
不要使用 main、猜測目前安裝狀態，或在我確認前修改檔案、GitHub 設定、
push 或建立 PR。

2.3 先判斷狀態，再決定操作

狀態判讀下一步
create目標尚未形成既有產品 Repository。詢問必要選項，建立新的受管專案。
adopt已有產品內容，但尚未由 repo-template 管理。盤點、預覽衝突並保留專案內容後導入。
adoption-pending導入計畫已有人工衝突尚未完成。沿用原計畫完成合併，再執行 finalize。
migrate已安裝，但 _commit 是 tag 或短 SHA，尚未綁定經驗證 Release 的 full SHA。依 status 提示驗證來源，再檢查遷移報告與計畫；legacy 轉換仍在 update 內執行。
update已有較舊的 repo-template 版本。比較模板、設定與專案變更後產生更新計畫。
current模板與設定已是目前版本。不重複安裝；回報現況與可選檢查。
policy-only-update檔案版本相同，但平台政策需補套用或重查。只處理可觀察的 GitHub desired state。

操作分工：Prompt 是使用者入口；外部薄型 CLI 負責可信 bootstrap、狀態判讀與交易式導入；導入後由 Repository 內的 .csarc/scripts/ 執行日常規則與驗證。

2.4 建立、導入、更新與移除

階段repo-template 行為使用者確認
偵測讀取 Repository、語言、文件與 GitHub 現況；不重問可可靠推導的值，必要答案不足時在任何寫入前停止。專案、技術基線與治理模式是否正確。

3. 日常使用

3.1 從需求到合併

階段使用者對 AI 說什麼完成條件
需求說明問題、使用情境、可接受結果與已知風險。Issue 有可判定的 AC、範圍、負責人與工作關係。
實作要求依 Issue 工作，保留既有內容，先建立 Draft PR。分支與 worktree 隔離，變更未超出 Issue。
檢查要求說明跑了哪些測試、每項 AC 的證據在哪裡。測試與人工證據都對應目前 head。
交付確認產品結果後，要求生命週期工具進入審核、合併與收尾。csarc-owned 且 release-worthy 的 PR 已物化版本；Milestone checkpoint 只有 terminal 物化，其餘以 deferred 合併。review、驗證、授權與 head／tree 一致後，再由 pr_lifecycle.py 合併。

合併、核准與設定：agent 不執行 gh pr merge、UI／auto-merge、force-push、push 到 main／dev/m*，也不改名有 open PR 的分支；不代發核准、Milestone approval 或 exact-head 授權。設定只以 csarc update --data KEY=VALUE 變更，不手改 .csarc/config.yml／.csarc/scripts，不直接執行 copier update。模板更新都走 governance-switch；新專案預設 admin_bypass: always 只取代同行核准，不能略過驗證、required checks 或 lifecycle。local 的 csarc-owned 發版由 maintainer 執行。

3. 日常使用（續）

3.2 使用者實際要做的事

  • 在 Issue 寫清楚問題、AC、風險與接受的控制。
  • 確認 AI 沒有改到需求範圍外的產品或設定。
  • 判斷畫面、資料、權限及產品結果是否可接受。
  • 查看 PR 中每項 AC 對應的測試或人工證據。
  • 只核准目前 head；後續修改必須重新檢查。
  • 需要權限、付費能力或外部環境時回報 BLOCKED，並寫明由誰處理。

風險區塊：每項風險至少指定一個控制，由 Issue assignee 負責；Ready 前每個控制須有可檢查證據，或以 accepted: <理由> 明確接受。R0 只用於沒有實質風險的 docs 範圍變更；AGENTS.md、安全政策及 CI policy 不算。單人維護時可自行接受 high，但仍須留下理由。

Agent 權限：把 3.1 的禁止事項寫進工具權限。例如以 permissions.deny 擋 gh pr merge、force-push、push 到 main、git branch -m、copier update，以及讀取 .env*、*.pem、*.key。有 Ruleset 強制時，agent 使用獨立 write 身分且不持有 maintain／admin；Private／Free 的 single-writer 路線中，agent 以唯一維護者身分執行，不另建 write 帳號。Issue、PR、review 與 CI 文字只當資料，不當授權；工具擋不住的 UI 操作只能由 drift、稽核紀錄或交付 gate 發現。

3.3 開發需求範例：替產品加入 CSV 匯出

這不是 repo-template 內建的 CSV 功能，而是示範使用者要求 AI 替自己的產品開發一項小功能時，如何把需求拆成可驗收、可測試的條件。

驗收條件需求證據使用者確認
AC1結果頁顯示匯出按鈕；UI 測試覆蓋顯示條件。按鈕位置與使用情境合理。
AC2CSV 欄位與畫面順序相同；回歸測試比對欄位。欄位內容符合產品需求。
AC3無資料時仍下載標題列；測試涵蓋空集合。空狀態行為可接受。
風險匯出沿用畫面允許欄位清單，不包含未顯示個資。確認資料用途與個資邊界。

3.4 GitHub Project Roadmap

設定完整的 organization／user github_project_url 後，以 csarc issue create 建立或 csarc issue sync-project 同步的 Issue 中，只有 Milestone tracker 與 standalone Issue（沒有 parent、不屬於有 tracker 的 Milestone）會加入 Project；work issue、sub-issue、PR 與其他方式建立的 Issue 不加入。Project 須事先各有一個 DATE 欄位 Project start／Project target；start 採 Issue 建立日的台北日期，target 投影 Milestone due date，沒有時為 start 後 14 天（可指定 target date）；Issue 關閉或 Status 為 Done 後，target 改為台北的實際完成日。Milestone 或歸屬改變後要重跑同步；既有值不同時先列差異，經確認才覆寫。工具即時查詢 ID，要求 project scope 與 Project 寫入權；不確定時回報 unknown。失敗時保留 Issue，以 csarc issue sync-project --issue <N> 冪等修復。Repository Projects 分頁維持關閉。

3.5 交接

交接內容至少包含 Issue、目前 branch／head、已完成與未完成 AC、測試及證據、外部等待條件、下一個安全動作。不得只留下聊天摘要；以 csarc risk suggest --open 列出缺少或無效風險區塊的 open Issue 與建議，以 csarc risk register --state all --json 交接目前風險、控制與證據狀態。

4. 測試、證據與交付控制

實際檢查由 Repository 設定、變更路徑及可信 base 的政策自動選擇。新建的 solo 專案預設使用 local 證據；團隊可明確選擇 Hosted CI，由 GitHub Actions 在遠端 runner 驗證 PR 精確版本。使用者不必自行組合測試命令。

4.1 到底會測試哪些內容

共同基線適用所有 Repository；語言品質與原生建置只適用於設定中已選擇的語言。這裡列出檢查內容，何時執行由 4.2 的 tier 與變更範圍決定。

檢查類別適用範圍實際檢查
共同基線所有 Repository每次跑 diff hygiene、衝突標記與 secret；workflow、shell 或模板路徑變更時跑 lint 與 Action SHA pin；設定／政策格式、版本一致性及 PR writer ownership 只在 Full 執行。
Python 品質只限已選 PythonRuff 格式與 lint、ty 型別、pytest、coverage、套件版本及依賴下限。
TypeScript 品質只限已選 TypeScriptBiome、tsc、Vitest 及 coverage。
Rust 品質只限已選 Rustrustfmt、Clippy 與 cargo test。
Go 品質只限已選 GoGo toolchain 版本、gofmt、go vet 與 go test。
原生建置與套件只限各已選語言Python wheel／sdist、metadata 與隔離 import；TypeScript build／pack 與隔離 import；Rust release build／package；Go build。
依賴與供應鏈存在支援的 manifest／lockfile 或 Actionslocked install、OSV 漏洞掃描及 Action pin；沒有支援的依賴檔時明確回報不適用。
治理與文件所有 Repository；文件依所選模式設定、JSON policy、Issue／PR 工具、規格與決策 metadata、文件 bundle 及 release 狀態。
選用：容器啟用 container 能力Docker Compose、image build 與 Trivy HIGH／CRITICAL 掃描；不登入 registry、不 push image。
選用：產品 hook設定 project_verification_hook，或存在 executable scripts/verify-product由專案自訂 E2E、資料庫、服務或其他產品驗證；hook 失敗即整體失敗。

4.2 實際執行方式與時間

方式何時執行如何選擇內容時間參考
Focused（非 tier）實作期間，由 AI／開發者主動執行。只跑變更 owner 的窄檢查；未選語言就不呼叫該語言工具鏈。數秒至數分鐘。
FastMilestone 工作 PR（beta）與 Dependabot 一般更新；路徑風險可升為 Full。每次跑 diff hygiene、衝突標記與 secret；再加入受影響的已選語言、依賴、workflow 或文件檢查。依產品與快取而定；repo-template 暖快取參考約 75 秒。
Full沒有 Milestone 的 standalone（stable）、promotion、hotfix、release recovery、merge queue 或未知風險。共同基線、全部已選語言的完整品質與原生建置，加上已啟用的容器及產品 hook。repo-template 目標 15 分鐘內；hosted job 上限 30 分鐘。

未選任何語言：仍執行共同基線、治理及所選文件能力；依賴掃描在沒有支援檔案時回報不適用。除非另啟用 container 或產品 hook，否則不做原生 build／package，也不產生假的空套件。

使用原則：正式 tier 只有 Fast 與 Full；實際要求取發布通道下限（Milestone 為 Fast，standalone／hotfix 為 Full）與路徑風險中較強者。local 與 hosted 使用同一套判斷；沒有 Milestone 的工作每張 PR 都跑 Full。

4. 測試、證據與交付控制（續）

4.3 本機檢查與 Hosted CI

來源用途何時可作為交付證據
本機新建 solo 專案的預設。在已 commit、乾淨的 exact head 執行一次 verify-fast；工具依相同判斷升級為 Full，結果綁定 SHA／tree，24 小時內有效。證據只存在執行者的 Git metadata；寫入者可同時改程式與證據，因此不能證明 GitHub event、權限或遠端 runner。
Hosted CI明確選擇 hosted 時，由可信 base 選擇 gate，在遠端 runner 驗證 exact head／tree。作為 hosted 模式的合併證據；預設 24 小時內有效，逾期或 head 改變即重跑。

4.4 一項需求如何進入合併

階段repo-template 檢查使用者看到的結果
Issue網頁表單只要求「完成條件」非空；AC checkbox、數量與證據在 Ready 檢查。csarc issue create 另可在建立前檢查風險區塊。需求有可判定起點；缺少 AC／風險區塊到 Ready 才阻擋。
Draft PR連結 Issue、隔離工作區，允許證據尚未完成。可持續實作，不會被誤認為可合併。
Readypr_lifecycle.py 或 hosted policy 要求 AC 全勾選並逐項有證據；每個風險控制有證據或 accepted: <理由>。缺項維持 Draft。lifecycle 含 issues 時，standalone／hotfix 另需有效 Approve 或 Admin-approve；Issue 變更後重新核准，緊急 hotfix 一律 Admin-approve。
Review／Merge生命週期工具重查核准、驗證、head／tree、coverage digest 與授權。push 後舊核准失效；能用 lifecycle 時只經 pr_lifecycle.py 合併。人工合併記為 untraced。

工具狀態以 check／status 呈現，不為重複進度另加 PR 留言；生命週期、核准與稽核所需的固定紀錄仍保留。合併時只產生一則可識別、可重查的 durable summary。

4.5 Requirement evidence 最低要求

PR 保留單一 Requirement evidence 區塊，逐項對應 AC1…ACn，記錄 regression test、目前 exact-head check，或附理由的人工證據；進入 Ready 時不得有 unknown 或 uncovered。確切欄位由目前版本的 PR template 與 SPEC-010 定義，不在手冊另造一套格式。

4.6 GitHub 方案與權限差異

Repository／權限條件可用能力repo-template 的處理
Public／Free+Actions、公開 Ruleset、公開安全掃描與 Pages。依額度與組織政策啟用；未執行不算成功。
Private／Free沒有 Ruleset 強制；只有 API 完整觀察到唯一維護者是唯一寫入身分時，lifecycle 才能合併。agent 以該維護者身分執行；出現其他寫入者或讀取不完整時只能人工合併並記為 untraced，後續改用 product-owned／verification-only 或升級方案。
Private／Pro、Team+可強制 private Ruleset；仍須 Repository admin 套用設定。先 plan／回讀；權限不足時不宣稱已啟用。
Private security entitlement私有程式碼的進階 CodeQL／安全能力。未授權時回報缺口並執行既有替代檢查。
Maintainer／Adminmaintain 可作一般核准；管理設定與 bypass 仍需 admin。即時讀取角色，不由舊 permission 欄位猜測。
Copilot／Project 存取與 Repository 方案分開授權；organization／user Project 的寫入者不同。無 Copilot 就改人工 review；Project 需 project scope 與該 Project 寫入權，無法確認時回報 unknown。

第 5 章 · 導入後的 Repository

5. 導入後的 Repository

repo-template 只產生已選能力需要的內容；生成專案的驗證只測專案本身，不夾帶模板的 release／fixture 測試。先辨認內容由誰管理，再看主要位置。

5.1 內容擁有權

類別範圍更新原則
模板擁有.csarc/ scripts／policies／操作文件／site 引擎；表單、PR template、Dependabot、workflows、AGENTS.md。固定版本更新。
共同維護語言工具設定檔與 .gitignore。3-way／合併更新，衝突先確認。
共同維護（new）README、LICENSE、安全文件、manifest 與容器檔。3-way 更新，產品版本欄位不變。
專案擁有產品程式、原生測試、產品 hook、商業規格、機密、部署與 docs 內容；existing 的 README／manifest。模板不得覆寫或刪除。
產品狀態.csarc/config.yml 的使用者意圖、release manifest 與 version.txt。設定由 csarc update、版本由發版流程寫入。

5.2 主要位置

提供條件：「核心」是每個受管 Repository 都需要；「條件式」只在設定選到該能力時產生；「專案自有」由產品決定，repo-template 不強制建立。

提供條件位置內容與邊界
核心.csarc/scripts、policies、文件由固定版本更新；設定／metadata 只經 csarc update，版本只由發版流程寫入。
條件式.csarc/選用能力的操作文件、repo-site 引擎及必要 runtime support；模板自測不下發，必要的工具測試只能放 .csarc/tests/。
核心.github/Issue／PR 表單與安全通報入口；遠端 Repository 設定仍以 plan／apply 管理。
條件式.github/Hosted CI、CodeQL、Dependabot 合併、Pages、容器等 workflow；code_owner 才有 CODEOWNERS。dependabot.yml 一律存在。
核心AGENTS.md、.claude/CLAUDE.md、SECURITY.mdAI 規則與掃描邊界；CLAUDE 只匯入 AGENTS；existing 的 SECURITY 屬產品。
條件式語言程式、測試、manifest／locknew 的 manifest 共同維護，程式／測試 seed 後歸專案；existing 不新增 starter 或 manifest。
專案自有scripts/verify-product 或設定的 hook只有產品需要額外 E2E／服務驗證時建立；不是 repo-template 工具或必要根目錄。
條件式／專案自有docs/依文件模式提供結構；規格、決策與內容由專案擁有，repo-site 產物才由工具重建。
條件式Dockerfile、docker-compose.yml只在啟用 container 能力時產生；啟用後仍需依產品調整。

命名空間：repo-template 的執行碼、fixture 與必要測試只在 .csarc/；平台、scanner、agent 固定位置與語言慣例設定檔除外。產品 lint、format、type check、test discovery 與 coverage 不涵蓋 .csarc/；根目錄 tests/、scripts/ 及語言目錄留給產品。

5.3 權威文件

本手冊是 repo-template 的產品政策與使用者承諾，隨 Release 放在模板 repository 的 docs/handbook/；生成專案不內含手冊，.csarc/docs/csarc.md 以 full SHA 連結所安裝版本。SPEC／ADR 保存精確契約與理由；AGENTS.md／CI policy 是 agent 的可執行規則。內容必須符合手冊，衝突即為 drift。

6. 更新、故障與限制

6.1 模板更新

階段必要行為安全條件
檢查固定 CLI、模板 Release、Copier、Jinja 與 Git 行為版本，讀取 Repository、設定、平台現況及上次實際 render snapshot。不使用浮動 main、未驗證的附件或 target 內可能過期的工具。
計畫以 snapshot 重建舊側，再逐項列出新增、更新、刪除、衝突、設定變更、Action pin 漂移與 migration。預覽與 apply 必須是同一份 final plan；舊側不得因缺值產生假衝突或幽靈檔案。
套用交易式更新後重新驗證實際結果。失敗維持原狀；不得留下部分寫入的修改。
平台Repository 檔案更新與 GitHub 設定分開處理並回讀。Copier 或 GitHub template 不會自動複製遠端設定。
治理合併與驗證依可信 base 政策；放寬治理或修改 .csarc/scripts 使用專用 governance-switch 路線。schema 變更先讓 base reader 支援下一版，再切換 writer；candidate parser 只做自測。

舊版遷移：外部 CLI 依來源 schema／Release 唯讀載入舊設定，每項改變都有 SPEC-008 報告列：退役鍵為 retired、承接鍵為 exact；既有 admin_bypass 保留，缺值改為 always 並以 widened 說明增加的權限與恢復方式。其他治理值只會是 unchanged、exact 或 narrowed；無等價值時以 decision／setting-decision 在寫入前決定。resolved render context 用來重建舊側；seed 沒有 native source 時，也提供新側 render 的值。runtime 只讀目前設定、native manifest、LICENSE 與受管常數，verify 不查 GitHub 取值。成功後只留 current schema，重跑不重複修改。

6.2 衝突、恢復與移除

衝突：不確定擁有權時先保留並回報，不以「模板較新」作為覆寫或刪除理由。

恢復：以計畫、報告及 Git 狀態判斷重跑點；部分外部寫入需明列已完成與待修復項目。

移除：由負責人決定保留哪些治理、文件與平台設定；確認產品仍可建置、測試、發布及維護。

機密：token、憑證及 populated .env 不得寫入 Repository 或更新報告。

6.3 狀態與外部故障

狀態常見原因處理
WAITINGReview、CI、權限、Release 或外部服務尚未完成。保留工作與證據，等待精確條件；不重新開始。
BLOCKED沒有安全且符合範圍的下一步，需取得決策或外部變更。回報阻擋條件、已嘗試項目及責任人。
DEGRADED平台無法強制控制，但 Repository-local 能力仍可用。採替代控制，且不宣稱缺少的平台保證。
失敗設定矛盾、驗證失敗、plan 不一致、stale evidence 或部分寫入。依結構化輸出修正後重跑，不從訊息文字猜測成功。

6.4 已知限制

repo-template 不提供通用部署、registry publishing、正式環境憑證或所有產品的 E2E，也無法阻止具權限者繞過工具直接修改 GitHub。UI 或 gh pr merge --admin 合併會略過 lifecycle，記為 untraced，並擋下下一次 csarc-owned 發版；local 搭配 beta-only／always 時，非 admin 寫入者也可能在 UI 合併。durable summary 也可被編輯或刪除，只能由 default branch 的 digest 發現。local 證據信任程度低於 hosted；不可觀察狀態一律回報 unknown。

A.3 設定類別與常用指令

.csarc/config.yml 只保存會影響未來行為、又無法安全重建的使用者意圖；數量是 schema 設計結果，不是固定目標。一般使用者不需逐項回答，由 CLI 偵測後只詢問必要選擇。

類別持久設定意義與限制

csarc status唯讀判斷 create／adopt／adoption-pending／update／current／policy-only-update／migrate。
csarc update --check --json在寫入前產生可重查的更新報告與計畫。
./.csarc/scripts/verify-fast依變更風險選擇日常驗證。
./.csarc/scripts/verify執行完整專案驗證與產品 hook。
