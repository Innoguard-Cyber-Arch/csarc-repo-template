# Repository instructions

## Responsibility map

- GitHub Issues and pull requests define work, progress, and evidence. Approved specs and ADRs preserve durable context. Add a plan only for cross-session, high-risk, or hard-to-recover work. Never store raw chat transcripts. [Journey 01](docs/index.html#method) defines work-item relationships and fields.
- `AGENTS.md` is the single source for AI working instructions. `CLAUDE.md` only imports it.
- Use one Git branch and one worktree for each writable task, so that concurrent changes stay isolated.
- Reusable validation lives in `scripts/` and tests. In this repository's hosted mode, the required hosted `verify` check selects the tier from trusted base code. It runs the risk-owned entry point once on the exact candidate. `scripts/check-trusted-verification` binds that GitHub-hosted result to the repository, commit/tree, tier, scopes, command, toolchain, runner, result, and freshness. Run local full only for a documented fallback or an explicit diagnostic request. Local success is contributor feedback; it never replaces the hosted check. Dependabot uses the same path, with no bot-specific bypass. Checked-in files under `.github/workflows/` are the only active GitHub Actions. [CI/CD settings](docs/index.html#testing) and [`docs/ci-policy.md`](docs/ci-policy.md) define the tier boundary and stage ownership.
- [Journey 08](docs/index.html#governance) and [`docs/ci-policy.md`](docs/ci-policy.md#審查與合併資格) own review requirements, merge eligibility, configured admin bypass, and the Actions-outage governance-switch route; the former quota fallback is retired. Do not restate or invent exceptions here.
- Copier owns template creation and updates. For existing-repository behavior, follow [Journey 09](docs/index.html#template-release) and [`docs/agent-install.md`](docs/agent-install.md).

## Scope and sources of truth

- This file applies to the whole repository. Read a nearer `AGENTS.md` only if a future subtree needs different commands or safety rules.
- Three documents serve three audiences; each is authoritative for its layer. `README.md` tells general users what the template is, whether to use it, and how to start. This file gives contributors and agents the executable workflow rules. `docs/index.html` is the appendix for decision rationale and technical detail. Do not restate this file's workflow rules in `README.md`; link to this file.
- The approved product handbook (`docs/handbook/handbook.md`) is the source of product policy and user commitments. `./scripts/build-handbook` renders it into `docs/handbook/index.html`. Specs and ADRs carry exact contracts. This file and `docs/ci-policy.md` carry executable rules. A conflict with the handbook is `drift` in the documentation review. To edit the handbook, get a new owner approval that replaces `docs/handbook/approved/` in the same change; see `docs/adr/durable-project-memory.md`.
- `copier.yml`, `template/`, `policies/`, and `profiles/catalog.yaml` are the product. `template/` is what downstream repositories receive. Root configuration governs this template repository.
- Use root `docs/specs/` for SDD current contracts. `docs/README.md` maps durable project memory.
- Use `docs/adr/` for decisions. In updated projects, also search the project-owned `docs/decisions/`. Never move or overwrite it automatically.
- [`SECURITY.md`](SECURITY.md) is the repository-wide scanner policy. [`.github/SECURITY.md`](.github/SECURITY.md) is the human vulnerability-disclosure policy. [`docs/security-scanner-readiness.md`](docs/security-scanner-readiness.md) lists provider capabilities, exact validation commands, scope, cost, and offline boundaries.
- Edit the root presentation through `site/`: Bilingual Markdown is in `site/content/`. Styles and interactions are in `site/static/`. Shared glossary, navigation, and config data are in `site/data/`. `scripts/build_repo_site.py` is the pure-Python render engine; `scripts/repo_site_blocks.py` parses the shared blocks. Run `./scripts/build-repo-site` to rebuild `docs/index.html`, `docs/index.en.html`, and the `llms.txt` indexes. Do not hand-edit generated outputs. `site/data/slide_inventory.json` records the ordered bilingual slide keys, tracks, and audiences that `scripts/check-repo-site-inventory` checks. When you add, remove, reorder, or re-track a slide, update it in the same change. `site/version.json` gives the engine and the presentation template independent versions; `scripts/check-repo-site-versions` checks them.
- Compose each repo-site page from the existing declarative block syntax in `site/content/*.md`. Do not add per-page CSS or HTML. `scripts/repo_site_blocks.py` parses the blocks, and named functions in `scripts/build_repo_site.py` render them (for example `render_slide`, `render_detail`, `render_config_guidance`). Hugo shortcodes and `site/layouts/` no longer exist. Pick the existing block that fits; do not invent a one-off layout: `{{< slide key=… track=… >}}` marks one page section. `{{< basic >}}` holds the default plain-language content of most slides. `{{< legacy >}}` is only for a slide that keeps bespoke fidelity or presentation styling (`legacy="true"` on the slide). Simple structural content skips both wrappers, and the slide body markdownifies directly (see the `files` slide). Inside `{{< basic >}}`, nest optional technical depth with `{{< detail >}}` (always-visible aside) or `{{< disclosure >}}` (collapsed `<details>`). Render config examples with `{{< config-guidance track=… >}}` from `site/data/config_examples.json`. Do not hand-write them.
- Mirror `site/content/_index.zh-tw.md` and `_index.en.md` slide by slide, with the same `key`/`track` and matching structure. Keep new `site/data/navigation.json` labels within the width that `scripts/check-repo-site-navigation` checks. `site/data/glossary.toml` only feeds the bilingual `llms.txt` index, not an in-page glossary widget.
- Keep decision records, the deck, and checked-in paths aligned. Do not describe a capability as active unless the template creates and verifies it.
- Write new or changed English text, including script messages, by [`docs/writing-guide.en.md`](docs/writing-guide.en.md). Write new or changed Traditional Chinese text by [`docs/writing-guide.md`](docs/writing-guide.md). Do not copy their rules into this file.
- Follow [`docs/documentation-policy.md`](docs/documentation-policy.md) for the template/content boundary, i18n, README, and licensing. Before you deliver a non-Draft pull request, compare the changed behavior and configuration with project-owned documentation. Then record `aligned` or a reasoned `not-applicable` against the exact head. `drift` and `inconclusive` block delivery.

## Working loop

1. At task start, run only `git worktree list --porcelain`. Keep unscoped cleanup for explicit maintenance; the creator still cleans up after merge. Before you plan or open an Issue or Milestone: List open Milestones and open Issues. Search open and closed Issues with two to four concrete problem or technology terms. Limit each query to 20 candidates. Read the body, comments, and linked pull requests of credible matches. Titles and labels alone are not decisions.
2. Use the work-item model in [Journey 01](docs/index.html#method). A Milestone is an optional dated delivery or release bucket; follow `docs/milestone-description.md`. Repository Projects stay disabled. If `github_project_url` in `.csarc/config.yml` names an organization or user ProjectV2: Only Milestone trackers and standalone Issues (no parent, not in a Milestone with a tracker) are added. Work Issues and sub-issues are skipped with a reason. `csarc issue create` sets an Asia/Taipei `Project start` (creation date) and `Project target`. The target is the Milestone due date, else `--target-date`, else start + 14 calendar days. After the Issue is closed or Done, the target is its Asia/Taipei completion date. After a Milestone or due-date change, or for an Issue created another way, run `csarc issue sync-project --issue <N>` or `--milestone <M>`. It shows a diff and asks for confirmation before it overwrites a different date (SPEC-009 §10; verified only with stubs, not against a live ProjectV2).
3. Before you create the work item, give a short prior-decision summary if the user can respond. If creation is already authorized, record each relevant `#N` as preserved, superseded, or rejected, with a reason, in the Issue supplement or Milestone `References`. If you find none, record the bounded queries you used. When a user confirms a durable architecture, tooling, security, compatibility, or platform constraint, summarize it in the work item. Then update the matching `docs/adr/` record in the scoped pull request. Never store a raw conversation transcript or promote an unconfirmed inference to a decision. Never silently reverse an earlier decision.
4. Use the checked-in Issue form and pull request template for the UI, the CLI, and the API. Do not create a second body format.
5. Open or select one GitHub Issue before you edit. Its acceptance criteria are the scope. Record `beta` for Milestone work. Record `stable` for a Milestone tracker, a standalone change, or a hotfix. Reject a conflicting declaration. State the locally required suite (channel floor plus path risk) and what hosted CI proves. Titles use 12-80 ASCII characters and at least three words, with no type prefix and no trailing period. At creation time, set one native Type, the assignee, and the applicable parent and Milestone. When research or a Feature grows into a dated delivery, the originating Feature Issue also belongs to that Milestone. Every resolving PR inherits the linked Issue's Milestone. On a Type-capable repository, do not repeat Bug, Feature, or Task as an Issue label. Keep only orthogonal labels such as `documentation`, `hotfix`, or `promotion`. Issue forms seed the lowercase classification label only as a portable fallback; lifecycle automation removes it after the native Type is set. A PR carries exactly one lowercase classification label. It comes from the linked Issue's Type, or from the fallback label when native Types are unavailable. `scripts/gh-issue-create` warns (never blocks) when a Milestone is likely missing. For body changes, use `scripts/gh-issue-edit` instead of raw `gh issue edit`. It warns locally before an edit invalidates an existing approval. It cannot intercept GitHub UI or direct API edits. After a Milestone closes, `gh issue edit --milestone <name>` cannot find it by name. Use the `gh api ... --method PATCH -f milestone=<number>` fallback in the Milestone safeguard section of `docs/ci-policy.md`. The creator is the default owner. UI creators assign themselves; CLI users and agents pass `--assignee @me`. Change the assignee only for an explicit handoff.
6. If new work exceeds the Issue, stop and open a separate Issue. Do not silently widen the current branch or pull request. If the new work comes from a problem found in a Milestone Issue, keep the new Issue in that Milestone, based on its `dev/m<N>` delivery branch. Open it standalone only if it clearly meets one of these conditions: It spans multiple Milestones, or it is a governance or tooling mechanism for all future Milestones, not this Milestone's feature scope. It is an urgent production fix that cannot wait for the Milestone to close. It comes from an external report (another collaborator or peer session) with no direct causal link to this Milestone's work. If you are not sure, keep it in the Milestone. The exceptions are narrow; they are not a default escape hatch.
7. Check each acceptance-criteria box in the Issue and each pull request checklist box only when it has real evidence. Complete all of them before you open the pull request or push the commit meant to satisfy the closing keyword. Do not check them box by box across pushes: each push re-runs the PR policy gate, so a known-incomplete push fails it (a retry storm, #430). Keep the pull request Draft while work is incomplete. The acceptance-checklist gate does not enforce completeness on a Draft, and it revalidates in full when the PR becomes ready for review; see the "Acceptance-checklist 驗證時機（#573）" section of `docs/ci-policy.md`. Risk controls: every work Issue carries the `#### 風險與控制` block in its 補充, with one row per risk, at least one control, and the assignee as Owner. Use `R0` only for docs outside `AGENTS.md`, `SECURITY.md`, `.github/SECURITY.md`, and the CI policy. Before Ready, the pull request's one `## Requirement evidence` section maps every acceptance criterion (the ordered top-level 完成條件 checkboxes, AC1..ACn) and every risk ID. Each maps to exact-head evidence, a reasoned `manual:` link, or, for a risk, a visible `accepted: <reason>`. Never invent evidence or use `R0` or `accepted:` to hide a real risk (docs/specs/SPEC-010-issue-risk-controls.md). Finalization: keep independent implementation and focused checks parallel, but serialize the expensive finalization window per destination base. In one parent/subagent tree, a worker reports `READY_TO_FINALIZE` with its Issue, branch, head, and base, then yields while the parent chooses the next candidate. Independent sessions that share one clone run `scripts/finalization-queue announce --issue <N> --base <branch>` from a clean worktree. They continue only when `status` reports `ready`. A waiting agent reports the earlier Issue and yields; it does not busy-poll. The expiring queue is advisory. It never grants authorization or replaces the remote lifecycle lease. Release candidate: for CSARC-owned release-worthy work, the selected agent updates from the current destination base. It then runs `python3 scripts/release_policy.py prepare-candidate --sha HEAD --phase <beta|stable>` and reviews the result. It commits only the governed version surfaces and CHANGELOG, as the final commit of the same pull request. Milestone work uses `beta`. Milestone promotion, standalone work, and hotfixes use `stable`. Title type: the highest Conventional Commit type on the branch must equal the PR title type, because the squash merge keeps only the title (step 12). `verify-delivery-version --pr-title` rejects a mismatch before merge (#1137). Checkpoints: if the Milestone tracker declares `### Checkpoints` before approval, only the terminal Issue of each checkpoint materializes and publishes the beta. Other Milestone work merges without a version (`deferred`) and must not run `prepare-candidate` (see `docs/milestone-description.md`). If exact materialization, current-base ancestry, evidence, or lifecycle authorization is missing, keep the pull request Draft, keep the warning, and do not merge. Never defer version creation to a post-merge version pull request. Before a Milestone promotion PR becomes Ready, record the batch-level ADR and documentation review that [`docs/ci-policy.md`](docs/ci-policy.md#milestone-promotion-的-adr-與文件對齊1176) requires.
8. Start a Milestone Issue from the Milestone's one short-lived `dev/m<milestone>-short-slug` delivery branch. Start an Issue without a Milestone from current `main`. If independent changes must soak or ship together, create a real Milestone; do not use a catch-all branch. Run `scripts/gh-issue-develop <issue> --base <base> --name type/<issue-number>-short-slug` for the native Development link and the pre-creation name check. Use its guarded `--repair-from <old-branch>` only before a pull request exists. GitHub closes an open pull request when its head branch is renamed, so never rename or delete an open PR's head as an automated repair. Follow `docs/ci-policy.md` for the explicitly authorized `dev/i*` canary, synchronization, promotion, hotfix, and release-recovery routes. If a pull request is stacked on another work branch, retarget it to the shared integration branch when the base pull request is ready to merge, before that branch is squash-merged and deleted. GitHub auto-closes a pull request whose base branch no longer exists; it does not retarget it. Recovery needs a new pull request from the same head branch, which loses the original number, reviews, and comment history.
9. Inspect the existing implementation, make the smallest coherent change, and preserve unrelated user work.
10. Add or update the narrowest regression check that proves non-trivial behavior.
11. While you iterate and before an ordinary push, run scoped or focused checks for the owners you touched. CI selects fast or full from the changed paths and the delivery stage (`docs/ci-policy.md`). Docs-only work is a fast-scope optimization, not another tier. In hosted mode, the pull request owner does not rerun the aggregate fast or full suite locally only because CI selected that tier. The hosted `verify` check runs it once on the exact candidate and gives the merge evidence. Use `./scripts/verify-fast` or one `scripts/verify-stage-*` only as a broader local diagnostic. Local full results never replace hosted evidence outside a documented fallback's boundary.
12. Create an automated pull request as Draft with `scripts/pr_lifecycle.py create`. It requires the checked-in PR body, a clean worktree, and a pushed exact head. Do not create a Ready PR and convert it back. Before any later automated Ready/Draft, authorization, metadata, or merge write, acquire the remote lease and use `scripts/pr_lifecycle.py`; otherwise stay read-only. This includes a configured admin-bypass PR (Issue #918): use `pr_lifecycle.py merge`, not a manual `gh pr merge --admin`. Journey 08 owns the merge rules. Pull request titles use `type(scope): summary` in ASCII: type is one of `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, or `revert`; the scope is optional lowercase `[a-z0-9._/-]`; `!` before the colon marks a breaking change; the `title` check enforces this. The squash commit and any release notes take this title, and release intent reads its type (`!` major, `feat` minor, `fix` or `revert` patch, others none), so name the highest-impact type among the branch's commits.
13. An Issue implementation stays active through merge and post-merge closeout, unless the user explicitly limits the task. After merge, confirm all of these: The exact head merged, and the linked Issue reached its expected state. The configured release, or the explicit no-release decision, completed with readback. The source branch and lifecycle lease were removed or intentionally kept. No required external state is pending. Then leave the task worktree and run `./scripts/cleanup-worktrees --apply --worktree <path> origin/<pull-request-base>` from another checkout. Never remove another task's worktree, or a dirty, locked, detached, unmerged, or unverifiable worktree. When the lane is no longer necessary, run `scripts/finalization-queue leave --issue <N>`.
14. Report `WAITING` with the exact condition when review, CI, release, permission, or other external state is pending. Report `BLOCKED` only when no safe progress remains. Report `DONE` only after step 13, with the changed behavior, verification evidence, and any remaining limitation. A worker then reports `ARCHIVE_READY` and exits or yields. The parent or client archives the session after the final report, because Codex cannot archive a running task; the worker never claims self-archive.
15. Open every new Issue with `scripts/gh-issue-create`. It runs `scripts/validate-issue-title` on `--title` before it calls `gh issue create`. At minimum, run `scripts/validate-issue-title "<title>"` first, so that the step 5 title rule fails locally, not later in hosted Issue triage.
16. Before you start or resume work on an existing branch or pull request, run `scripts/check-branch-fresh <branch>`. It confirms that local still matches the current tip of `origin/<branch>`. Recent local work does not prove it: origin can advance or be force-pushed or rebuilt.

Reuse a host-managed worktree. Never force a branch into multiple worktrees. Never remove a worktree that another task owns or that has uncommitted changes. Keep active checkouts, worktrees, environments, and caches on local storage. If you are assigned a cloud-synced File Provider path, switch to a local checkout without routine user confirmation and preserve existing changes. Worktrees isolate files; integration still uses PR, CI, review, and final verification.

Never push directly to a delivery branch, invent successful evidence, create or dispatch release tags manually, or bypass the linked governance policy.

Duplicate triage can close an Issue without code changes if it links the canonical Issue and uses GitHub's native duplicate reason. If a change modifies the shape of an Issue or pull request body, migrate the existing bodies before you close it. Otherwise, create and link a follow-up Issue first.

## Commands

- Environment setup: `uv sync --locked --python 3.14`.
- Python iteration: `uv run ruff check <paths>`, `uv run ty check <paths>`, and `uv run pytest <test-path>`.
- Site source check: `./scripts/build-repo-site --check`.
- Security smoke: `./scripts/security-smoke` runs four existing offline owner self-tests. It is not an AI security scan and not part of every routine gate. [`docs/security-scanner-readiness.md`](docs/security-scanner-readiness.md) lists the exact commands and limits.
- Full verification entry point: `./scripts/verify-template.sh`. Hosted CI runs it when the trusted plan selects `full` (see `docs/ci-policy.md`). One `scripts/verify-stage-*` script rechecks one stage but does not attest the aggregate result.
- Trusted hosted evidence after a run: `./scripts/check-trusted-verification <head-sha> --github-repo <owner/repo>`.
- Copilot review loop (`copilot_review: allowed` in `.csarc/config.yml`): after each push, `python3 scripts/review_gate.py status --repo <owner/repo> --pr <N>` lists Copilot's findings on the current head and the unresolved threads. Fix them locally, push, then answer and resolve the threads. Repeat until Copilot's review of the exact head is clean and the `review` check passes. Then merge through `scripts/pr_lifecycle.py`. A maintainer approval of the exact head is a valid alternative. See the "Copilot 審核模式（#752）" section of `docs/ci-policy.md`.
- Release execution: `release.yml` only publishes a candidate that the merged PR already materialized and reviewed. Hosted publication is the default. When Actions or webhook delivery is unhealthy, run the same `scripts/publish-release` locally under the maintainer's admin identity. Never create a replacement version PR or a tag by hand; see the release fallback section of `docs/ci-policy.md`.
- Milestone creation: `scripts/create-milestone` creates the GitHub Milestone (with a real due date) and its tracker Issue in one atomic step. Before you dispatch work under an existing Milestone, run `python3 scripts/sync_milestone_state.py preflight --repo <repo> --milestone <N>`. It revalidates the due date, the tracker title, and the `Lifecycle Issue: #N` link, so the first PR does not fail `Validate Milestone approval`. See `docs/milestone-description.md`.

## Editing boundaries

- Keep shared policy changes synchronized between root and `template/` where both layers consume them.
- Do not weaken generated-project checks to make template tests pass.
- Keep GitHub Actions pinned to full commit SHAs, with the readable release tag in a comment.
- Do not hand-edit generated lockfiles. Use uv or pnpm, so that integrity metadata stays valid.
- Do not create a separate GitHub repository for testing or validation. Use local temporary projects or this repository's Issues, branches, pull requests, and Actions.
- Do not add a language without executable create, existing-repository adoption, update, and native-toolchain verification. Deployment targets and platform integrations still require a real consuming repository.
- Write comments in source code in English. Keep formatting and lint details in their executable configuration; do not copy them here.

## Platform capability and automation

- Keep desired automation declarative and testable. Do not assume organization or enterprise administrator access.
- Never extract or persist `gh auth token` as project configuration. Never require a personal token for the portable baseline. Never treat a permission error as proof that a capability is available.
- Report a blocked or unavailable capability explicitly. Never claim that a release, deployment, review gate, or other control succeeded when it was skipped or unsupported.

## Safety

- Never commit secrets, tokens, private keys, or populated `.env` files.
- Review the plan output before you apply repository settings. Do not operate production or external infrastructure without explicit authorization.
- Do not bypass required checks or supply-chain verification. Journey 08 is the only source for the configured admin approval bypass, including its exact-head authorization and audit requirements.
- If you read a shell pipeline's result from `$?`, make the judged command the last stage. `cmd | tail -N; echo $?` reports the exit code of `tail`, not of `cmd` (false "it passed" claims in Milestone 8). Redirect to a file and check separately: `cmd >log 2>&1; status=$?`. For pull request checks, use `scripts/check-pr-policy-status` (see the "PR policy 逐 step 判讀（#513）" section of `docs/ci-policy.md`). Do not grep `gh run view --log` or trust only the job-level output of `gh pr checks`.

## Code Review Rules

- Flag documentation or slide claims that do not match files the template actually creates.
- Flag changes that reduce required checks, permissions safety, artifact verification, or product-source preservation during Copier updates.
- Require tests for behavior changes and synchronized lockfile updates for dependency changes.
- Treat public interfaces, release behavior, workflow permissions, and secret handling as high-risk review areas.
